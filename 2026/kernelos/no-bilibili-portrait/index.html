禁止竖屏 | Android 系统的 Root 和 Hook

发表于2026-08-09|更新于2026-08-16|Kernel&OS

一直从最初的一键 root 到现在我使用的 KSU，一直在用但不了解原理，这里统一学习了解下 root 时系统底层发生了什么，各种 root 生态下插件系统在做什么。顺便修复、发布、接手我一直再用的 LSPosed 插件。

一台被 Root 的 OnePlus 13

先简单介绍下当前我的设备，以及我 Root 常见的使用方式。

设备 Root 核心组件

我这里有两台设备用于验证：

Redmi Note 12 Turbo（Android 13，HyperOS 1.0），用于验证 Magisk 的行为，安装了 Shamiko 来隐藏 root，同时也安装了 LSPosed：

  • Root 方案：Magisk v28.0，用户空间 root，修改 boot.img 的 initramfs。
  • Shamiko：Zygisk 模块 v1.0.1，白名单模式隐藏 root 痕迹。
  • LSPosed：社区维护版 LSPosed_mod。

OnePlus 13（Android 15，ColorOS 15），用于验证 KernelSU 的行为和插件修复：

  • Root 方案：KernelSU。内核级 Root，代码跑在 Linux 内核里，不改动 /system 分区，隐蔽性和兼容性都比传统方案好。
  • ZygiskNext：独立实现，给 KSU 提供 Zygisk API。版本 1.4.3。
  • ZygiskAssistant：隐藏 root 痕迹；对目标 App 启用 Umount modules 后，在该进程内 hook 检测调用。
  • LSPosed：Android 15 上官方 LSPosed (v1.9.2) 已不兼容。需要用社区维护的 LSPosed_mod（2026 年 8 月官方已经修复）。

常用模块与应用

这些模块和应用运行在不同的层级，理解这一点能更快判断它们的能力，后续会重点介绍它们各自原理：

  • LSPosed / Xposed 模块：代码被注入到目标 App 的进程里，在 Java/Kotlin 层通过 LSPlant 做 ART 方法级的 hook。能改勾选进作用域 App 的行为（改返回值、拦截调用、改 UI）。
  • Riru 模块：Zygisk 的前身，同样是 Zygote 注入，但靠替换 libmemtrack.so（一个被 Zygote 加载的库）来搭车启动自己的代码，再 hook Zygote 的 fork 回调，隐蔽性差，已被替代。
  • Zygisk 模块：比 LSPosed 更底层，在 Zygote fork 每个 App 进程时以 native 代码注入，早于 App 自己的代码执行。能做 LSPosed 做不到的事：隐藏 root 痕迹、修改进程内存、拦截系统调用。
  • Shizuku 应用：通过 ADB/无线调试启动一个特权服务进程，调用普通 App 不能直接调的系统 API（如安装/卸载、修改权限），不需要 root。权限级别介于普通 App 和 root 之间，这里不展开介绍。

Root 原理：Android 从内核启动到应用

Linux 的用户都知道，每个进程都有一个用户 UID，内核在权限检查的时候，对于 UID 为 0 的 root 用户，跳过几乎所有检查。但 Android 不止有 UID，还有 SELinux。SELinux 在内核之上又加了一层强制访问控制，即使是 root，SELinux 策略也有权力阻止进程对于某些资源的访问。所以现代 Android 上的 root，光拿到 UID 0 不够，还得能绕过或修改 SELinux 策略。

Android boot 到应用程序

要理解 root 怎么注入，先要理解 Android 是怎么启动的。

Bootloader：按下电源键后，SoC 的 ROM 代码加载 Bootloader。Bootloader 验证 boot.img 的签名（如果有 BL 锁，签名不对就拒绝启动），然后把它解压到内存。因此刷机的第一步往往是解锁 BL，让 Bootloader 跳过验证、接受修改过的 boot.img；同时也可以开放 bootloader 的刷入命令。

Linux Kernel：boot.img 里包含 kernel。内核启动后挂载根文件系统（从 initramfs 或 system 分区），然后启动第一个用户空间进程，init（PID 1）。init 是所有用户空间进程的祖先，这一点和普通的 Linux 发行版类似（通常为 systemd），Android 的 init 实现由 Google 自己定制，它解析 init.rc 脚本，按顺序拉起守护进程。

init → Zygote：init 启动的守护进程中，最关键的两个是 servicemanager 和 Zygote。Android 的系统服务（Activity 管理、包管理、通知等）都运行在 System Server 进程里，App 与这些服务通信需要跨进程调用，而 servicemanager 充当这些服务的注册中心，每个服务启动后在这里登记自己的名字，App 调用前先来查询对应的句柄，查到后直接与目标服务通信。这套跨进程调用的底层机制是 Binder，一个 Android 特有的内核驱动，与传统 Linux IPC（如管道、socket）不同，Binder 让跨进程调用以 RPC 的形式呈现，通信双方无法伪造身份。Zygote 则是应用进程孵化器，做两件事：（a）启动时预加载所有系统 Framework 的 Java 类（Activity、View、Service 等），之后 fork 出的 App 进程直接继承，不用各自加载；（b）打开 socket 等待 System Server 发来的 fork 请求，应用进程都是由 Zygote fork 产生。

System Server → 你的 App：System Server 是 Zygote fork 出的第一个子进程。它启动 ActivityManagerService（AMS）、PackageManagerService（PMS）等核心系统服务。当你点一个 App 图标时，Launcher 通过 Binder 告诉 AMS 启动这个 App，AMS 发指令给 Zygote 去 fork 一个子进程——这个子进程就是你 App 的进程。fork 发生在 Zygote 身上的那一刻，继承了 Zygote 已预加载的所有 Framework 类，然后 System Server 再告诉这个进程“加载你自己的 dex”。

SuperSU 一键 root

最早的 Android root（一键 root 时代，Android 4.4 之前）是通过一些 Kernel 的漏洞，非常简单。直接往 /system/xbin/ 塞一个有完整 rws 权限的、定制的 su 二进制。App 申请 root 直接 fork 执行 su，su 会通过 socket 连接 root 管理程序，弹窗确认，通过后完成 root 获取，可以通过 su 直接执行一些特定的二进制或者获得交互式的 shell，一般并非 App 本身直接变成 root 权限。但随着 Android 4.4 到 5.0，Google 做了很多安全补丁：

  • dm-verity（4.4）对 /system 分区做块级哈希校验，改数据则分区拒绝挂载；
  • SELinux enforcing（5.0）在权限层面加以限制——即使进程是 UID 0，只要 SELinux 策略禁止，就不能写 /system 也不能执行不受信的 setuid 文件。

这时候，root 已经走上了现在主流 root 的路线了，即修改 boot.img。

Magisk：用户空间的 systemless overlay

通常来说，现代 root 的流程都是：开启 USB 调试、OEM 解锁、解锁 BL、patch boot.img 再刷回去。

Magisk 修改 init_boot.img 中的 initramfs，在 init 启动时 注入自己的 magiskd 守护进程。这一步 Magisk 还会 patch sepolicy，给自己创建一个特权 domain，magiskd 一启动就是 UID 0 + 特权 domain，SELinux 自己的策略允许它做提权操作。

提权本身不依赖 overlay：magiskd 是 init 启动的 root 守护进程，App 的 su 客户端通过 socket 连它，magiskd fork 出 root 子进程即可提权。Magisk 的 su 不是 setuid 二进制，这点跟 SuperSU 时代根本不同。su 是个客户端：App execve su 后进程仍然是 App 的 UID（没 setuid 位，内核不提权），su 通过 socket 连 magiskd 请求授权，magiskd 查授权数据库确认后 fork 出一个 UID 0 的子进程，通过管道连回 App，这样就得到了一个 root shell。SELinux 禁止执行 setuid 文件这条规则对 Magisk 不适用，根本没有 setuid 文件被执行。su 只是客户端，真正有 root 的是 magiskd。

值得注意的是，Magisk 依然大量 依赖 overlay，尽管提权的过程本身已经不需要了：（1）su 的 path，让 su 在 /system/bin/su 能被 App 找到执行，Magisk 用 tmpfs 把 magisk 二进制 overlay 到 /system/bin/magisk，再让 /system/bin/su symlink 到它；（2）模块挂载，模块文件通过 Magic Mount（bind mount 到 /system），有模块才挂。magiskd 自己的工作目录在 /debug_ramdisk（Android 11+，老版本用 /sbin）的 tmpfs 上。物理上 /system 分区没有 su 这个文件，但 overlay 之后应用程序看起来能找到。

整套方案在用户空间运作，非常成熟，也是目前应用最广的方案。Magisk 附带 Zygisk 能力，它把 magisk 二进制伪装成 libzygisk.so 挂到 /system/lib[64]/，启动时设 ro.dalvik.vm.native.bridge=libzygisk.so，利用 ART 的 Native Bridge 机制让 Zygote 加载它，从而让后续每个 fork 出来的 App 进程都自带 Magisk 的代码（老版本 Zygisk 是替换 app_process，新版改用 Native Bridge 更隐蔽，Zygisk 的内存也会变成匿名内存躲字符串扫描）。现代 LSPosed 就跑在这条 Zygisk 通路上，在 Java/Kotlin 层通过 hook ART（Android Runtime）方法来修改 App 的运行时行为；更早的 Xposed 生态则另有注入路径，并不依赖 Zygisk。

KernelSU：内核空间的 kprobe hook

KernelSU 是最近几年比较热门的新兴 root 方案，不靠 initramfs patch，而是在内核里 hook。它用 kprobe（Linux 内核自带的探针机制，本来给内核调试用，能在任意内核函数入口插断点，内核执行到那里就跳进你的处理函数）或 manual hook。KSU 编译成 kernelsu.ko 内核模块（或编进内核镜像）加载后，用 kprobe 去 hook execve、stat、faccessat 这几条系统调用。早期 KSU 曾用 hook prctl 传魔数的方式提权，现代版本已改用 execve hook。

KSU 在内核里 hook 了 stat/faccessat，让 /system/bin/su 这个路径对授权的 App “看起来存在”，但物理上根本没有这个文件（cat /system/bin/su 会报 No such file or directory，只有 stat/ls 能看到它），是个内核 hook 伪造的“幽灵文件”。App exec /system/bin/su 时，KSU 的 execve hook 拦截这次执行，检查白名单（/data/adb/ksu/.allowlist）。授权通过后，KSU 在内核里把 su 进程的 cred 改写成 UID 0，绕过 DAC（Discretionary Access Control，自主访问控制，即传统的 UID 权限检查），同时把它的 SELinux 上下文切到一个 KSU 自建的特权 domain（如 u:r:su:s0，由 App Profile 配置），SELinux 对这个 domain 不再拦截。su 没有物理文件，也就没有 setuid 位可言，提权全在内核里完成。

KSU 还注册了一些 LSM（Linux Security Module）hook 做辅助和隐藏。因为 KSU 的 kprobe/manual hook 挂在 execve、stat、faccessat 等系统调用入口，这些调用都会过一遍 KSU 的检查，比没装 KSU 的机器慢一点点。检测 App 测这些系统调用的耗时，跟干净设备的基线比，异常慢就暴露了 hook 的存在，和密码学的时序攻击基本相同，所以 KSU 专门做了 LSM hook、调用黑名单等手段来抹平时序痕迹。此外 KSU 会隐藏自己的内核符号，/proc/kallsyms 里查不到 KSU 的符号（实践中 grep ksu 只能匹配到 ext4_chksum 这种 “chksum” 含 “ksu” 的误匹配），这也是反检测的一部分。

Magisk 这里其实有两套机制。su 授权：谁能拿到 root，由 Magisk 的授权数据库决定，App 调 su 时 magiskd 查库放行或拒绝。DenyList（排除列表）：一份「要对谁动手脚」的名单。若打开 Magisk 的遵循排除列表（Enforce DenyList），Magisk 自己会对名单内 App umount、不注入 Zygisk；若装 Shamiko，则应关掉 Enforce，把名单交给 Shamiko 读（黑名单模式），或干脆开 Shamiko 白名单模式、不再用这份名单选目标。KSU 的提权则是另一套白名单：默认没有任何 App 能拿到 root，只有 KSU Manager 中明确授权的 App 在调 exec("su") 时，KSU 查 allowlist 里有这个 UID 才会改写 cred 授权。

实际验证（OnePlus 13，KSU + ZygiskNext 1.4.3 + LSPosed_mod + ZygiskAssistant）

连接设备（与 Magisk 相同，Android 11+ 无线调试）：

这里我安装了 ZygiskAssistant，但它只在目标 App 进程内 hook 隐藏 root 痕迹。adb shell 不是它的注入对象，所以能正常看到 KSU 的所有痕迹。

su 是内核 hook 伪造的“幽灵文件”（物理不存在）

ls（走 stat）能看到 su，但 cat（走 open）报 No such file。su 物理上根本不存在，是 KSU hook stat/faccessat 伪造的“幽灵文件”，execve 时被 hook 拦截做提权。这跟 Magisk 的 /system/bin/su -> ./magisk 真实软链接完全不同。

KSU 自建 permissive su domain u:r:su:s0，这是 KSU 的特权 SELinux 上下文，Magisk 设备是 u:r:magisk:s0。全局 getenforce 仍然是 Enforcing，但 KSU 把切换到这个 domain 的进程豁免掉 SELinux 检查。

无 Magisk overlay 痕迹

系统核心分区（/system_ext、/system_dlkm）是 erofs 只读，apex 是 ext4 只读（loop 设备），都是原生系统挂载，没有任何 Magisk 那种 magisk on 的 tmpfs overlay。这也印证了 KSU 提权不靠 overlay。

ZygiskNext 守护进程（后面 Zygisk 注入一节会解释它为什么常驻）

KSU 白名单里 USK 是 KSU 的 magic number，后面跟着包名。这是 KSU 白名单制的体现，Magisk 的授权数据库是 SQLite，不是二进制格式。

APatch：直接 patch 内核二进制

APatch 的核心是 KernelPatch（KP），只用一个 stripped kernel image（无源码、无符号表）就能 patch 内核。它靠 CONFIG_KALLSYMS（内核编译时保留的符号表）定位内核函数地址，然后做两类 hook：inline hook 找到目标内核函数，在它的机器码开头插入跳转指令，跳到 KernelPatch 自己的处理代码，用于隐藏自身、绕过 SELinux 等；syscall table hook 则往内核的 syscall 表里新增一个 syscall，叫 SuperCall，用于提升权限，同时也做了模块管理等。

APatch 的 su 二进制持有 SuperKey（patch 时生成的凭证），调 SuperCall 时把 SuperKey 传进去。KernelPatch 在内核里校验，key 对了就把调用进程的 cred 改成 root，key 错了则什么都不做，调用方不受影响。这个 SuperKey 是安全门：新增的 syscall 任何进程都能调，没有 key 的话任意 App 都能触发提权，所以用 key 当密码，只认持有者。

任何 ARM64 内核（只要开了 KALLSYMS）都能用，不限于 GKI（Generic Kernel Image）内核，也不需要厂商适配 KSU。模块上，APatch 提供 KPM（KernelPatch Module，往内核注入任意代码）和 APM（类似 Magisk 模块的 userspace 模块）。

SELinux 三家各有各法：Magisk 改 sepolicy 策略给 magiskd 的 domain 开口子，KSU 自建一个 permissive 的 su domain 把进程切过去，APatch 直接 hook 掉 SELinux 的检查函数，对已授权的进程直接放行，不改策略也不换 context。

这套方案我还没有实际使用过，上面列举的 SuperSU 时代方案、Magisk、KernelSU 则是亲身体验过的。

Root 生态

Root 模块：systemless 改系统的标准方式

Root 模块是 root 生态最实用的部分：不改系统分区，用一套约定的目录结构把替换文件、启动脚本、配置塞进去，重启后生效。现代的三家 root 工具都支持，但实现和兼容性有差异。

模块怎么组织。一个模块就是个目录，安装包是个压缩包，装到 /data/adb/modules/<模块id>/，核心文件：

  • module.prop：元信息（id、name、version、author、description），管理器靠它识别
  • system/：要覆盖到 /system 的文件，目录结构镜像系统路径（system/bin/foo 盖到 /system/bin/foo）
  • post-fs-data.sh：boot 早期（post-fs-data 阶段）跑的脚本
  • service.sh：boot 后期（系统起来后）跑的脚本
  • system.prop：要设的 system property
  • sepolicy.rule：SELinux 策略补丁
  • uninstall.sh：卸载时清理

实现原理。system/ 不是真往 /system 写文件（dm-verity 锁着），而是 root 工具在 init 阶段用 overlay / bind mount 把这些文件盖到对应路径上。物理分区没动，逻辑上系统看到了替换后的文件。因此，无论哪种 root 方式，只要安装这些插件，都需要去覆盖修改 system。脚本在 boot 特定阶段以 root 跑，能挂载、改配置、起服务。

能做什么。换系统字体、改 hosts 去广告、替换音效驱动（Viper4Android）、改 build.prop 属性、boot 时起自定义服务、装命令行工具到 PATH、改 SELinux 策略。本质是"不刷机改系统"，而且卸载干净，删模块目录即可，不残留。

Zygisk 注入

Android 所有 App 进程都是 Zygote 的 fork。Zygote 在启动早期就把系统 Framework 类全部预加载好，之后每个 App 进程 fork 时继承这些已加载的类。这带来两个效应：（1）App 启动快（共享预加载），（2）如果在 Zygote fork 前往它体内注入代码，之后所有 App 进程都会自带这段代码。

Zygisk 做的就是在 Zygote 体内注入代码。现代 Magisk 的做法是把 magisk 二进制伪装成 libzygisk.so 挂到 /system/lib[64]/，启动时设 ro.dalvik.vm.native.bridge=libzygisk.so，利用 ART 的 Native Bridge 机制让 Zygote 加载它（magiskd 在 init 阶段跑起来，早于 Zygote 启动，负责设这个 property）。Zygote 加载 libzygisk.so 时实际跑的是 Magisk 的代码，先把 Zygisk 跑起来再正常当 Zygote。老版本 Magisk 的 Zygisk 是直接替换 app_process 二进制（app_process 就是 Zygote 本身，init 启动 Zygote 就是 exec /system/bin/app_process），新版改用 Native Bridge 更隐蔽，Zygisk 的内存也变成匿名的，躲字符串扫描。注入之后：

  1. Zygisk hook 了 Zygote 里几个关键的 “fork 后回调” 函数（nativeForkAndSpecialize / nativeForkSystemServer）。
  2. 每当有新 App 进程 fork，Zygisk 的回调被触发，在新进程里遍历所有安装的 Zygisk 模块，挨个调用它们的入口。
  3. 模块的 native 代码在新进程里执行初始化，获得和 App 代码完全同等的权限。

ZygiskNext 是 Zygisk 协议的独立重实现，给 KernelSU/APatch 用。它没有 magiskd 那个 init 阶段的 daemon，等它的代码能跑时 Zygote 早就启动了，没法在启动时被动注入，只能 ptrace 活着的 Zygote 往里塞 .so。ptrace 就是 GDB 调试器底层用的那套接口：附着目标、读写它的内存、改寄存器逼它调一次 dlopen 把 .so 加载进来。这里 KernelSU 提供内核级 root + 绕过 SELinux（ptrace Zygote 会被 SELinux 拦），ZygiskNext 拿这个 root 做 ptrace 注入。

实际验证

Magisk 的 Zygisk（Redmi Note 12 Turbo）：libzygisk.so 其实是 magisk 二进制伪装的（md5 完全一致），Zygote 的 maps 里加载了它，而 app_process 没被替换（还是原生 erofs），ro.dalvik.vm.native.bridge 被设成 libzygisk.so 后又用 resetprop 隐藏成 0。这印证了现代 Magisk Zygisk 用 Native Bridge 注入，不是替换 app_process。具体命令见前面 Magisk 章节的验证。

ZygiskNext（OnePlus 13）：ZygiskNext 以 KSU 模块形式安装（模块 id zygisksu），跑起来后有独立的守护进程 zn-nsdaemon，用 ptrace 往活着的 Zygote 注入：

三个 zn-nsdaemon 对应 ZygiskNext 支持的三种 Zygote（zygote、zygote_ocomp、zygote_secondary），与 ZygiskNext 模块描述 [✅zygote, ✅zygote_ocomp, ✅zygote_secondary] 完全吻合。Magisk 的 Zygisk 靠 magiskd 在 Zygote 启动前设好 Native Bridge，不需要再常驻一个专门去 ptrace 的进程；Zygisk 代码随后跑在 Zygote（以及 fork 出的 App）里。ZygiskNext 因为赶不上 init 阶段的被动注入，只能另起 zn-nsdaemon 主动 ptrace，所以多了这些独立进程。

LSPosed 模块

有了 Zygisk -> Zygote 注入这条通路，LSPosed 做的事就是把 Java/Kotlin 写的 Xposed 模块代码，加载进目标 App 的进程：

  1. Zygisk 回调触发后，LSPosed 的 native 层被调用。
  2. 它检查：这个 App 的包名，在某个已启用的 Xposed 模块的作用域（scope）中，如果在（比如 Portrait2Landscape 作用域含 tv.danmaku.bili），LSPosed 就把 那个模块 APK 里的 .dex 加载进当前进程的 ClassLoader
  3. 模块的 xposed_init 入口被反射调用，YukiHookAPI 启动，你的 onHook() 开始注册 hook。
  4. Hook 注册在执行层面调用 LSPlant（LSPosed 的 ART 方法 hook 引擎），修改目标方法的 ArtMethod 入口指针指向 trampoline。

禁止竖屏原理

有了前面的 root、LSPosed 原理之后，再看这些代码其实就非常简单了。

先从 Bilibili 讲起，Bilibili 有一个深链（deep link）机制：

  • bilibili://story/<avid> → 路由到竖屏"看一看"播放器。
  • bilibili://video/<avid> → 路由到传统横屏播放器。

原版 WankkoRee/Portrait2Landscape 把 hook 打在首页 feed 卡片的 Java 对象 BasicIndexItem 上。每个卡片有个 uri 字段，竖屏视频的就是 bilibili://story/...。Hook 机制：

  • hook 所有构造函数：对象创建后，读 uri 字段，如果是 story 打头，替换成 video。
  • hook setUri(String)：有代码后期修改这个字段时，拦截 setter 参数同样的替换。

这套机制在 Bilibili 7.x 及更早版本上完美工作。

失效：8.x 重构路由，绕过了卡片字段

Bilibili 更新到 8.x 之后，竖屏播放器的启动路径发生了根本变化。反编译 8.60.0 和 8.97.0 两个版本的 APK，确认了：

  • BasicIndexItem 类、uri 字段、setUri(String) 方法都还在，没被混淆，名字都和 7.x 完全一致。
  • 但是竖屏播放器的启动已经不再去读 uri 字段了。

新逻辑的本质等价于：

插件在 BasicIndexItem 构造函数里把 uri 改成了 video/<id>，但路由层 根本不看这个字段，直接拿了原始 avid 拼成 story/<id>。这就是为什么模块在老版本能用，到 8.x 彻底不生效 — hook 挂上了，改的字段没人读。

禁止竖屏代码分析

这个代码使用的是 YukiHookAPI，这是最常用的 Xposed 框架之一。模块代码分两块：Main.kt（入口 + 配置）和 Hook.kt（hook 逻辑）。

Main.kt：入口与配置

这个 @InjectYukiHookWithXposed 是 YukiHook 的注解，编译时触发 KSP（Kotlin Symbol Processing，Kotlin 编译期代码生成）生成真正的 Xposed 入口类。entryClassName = "Entry" 指定生成类名，要和 assets/xposed_init 里写的对应，LSPosed 靠这个文件找入口类。这个注解会让 KSP 在编译时生成一个叫 Entry 的类。它不在源码里，是框架的 KSP 处理器生成进你模块包里的，全名 cn.wankkoree.xp.portrait2landscape.hook.Entry。

xposed_init 指向 Entry（LSPosed 加载），每次作用域 APP 启动前（即 LSPosed 里面勾选的 APP），都会先执行 Entry，Entry 启动 YukiHookAPI，YukiHookAPI 调 Main，最终注册 init 和 hook。Entry 你不用写、不用看，编译时自动生成，改了 Main 上的注解它就重新生成。

isUsingResourceHook = false 声明不 hook 资源（布局/图片/字符串），只 hook 代码，省开销。IYukiHookXposedInit 是 YukiHook 的入口接口，要实现 onInit（配置）和 onHook。

值得注意的是这几个配置：

  • isEnableModulePrefsCache / isEnableModuleAppResourcesCache：缓存模块自己的 SharedPreferences 和资源，读取更快。
  • isEnableHookModuleStatus = true：开"模块已激活"自检（LSPosed 管理器里那个绿勾就靠它），建议开。
  • isEnableHookSharedPreferences = false：hook SharedPreferences 实现模块和宿主 App 共享配置（老 Xposed 玩法）。本模块没 UI 配置，关掉省开销。
  • isEnableDataChannel = false：模块和宿主进程互发数据的通道。用不上，关。
  • isEnableMemberCache = true：缓存反射查到的方法/字段。这个要开，hook 靠反射找目标方法/字段，每次跳转都反射会很卡，缓存复用就快。

onHook：encase 是 hook 作用域。val hooker = Hook() 建一个 hooker 实例。loadApp("tv.danmaku.bili", hooker) 和 loadApp("com.bilibili.app.in", hooker) 让同一个 hooker 在国内版 / 国际版两个包名进程里都激活。模块代码会被加载进作用域内所有 App 进程，但是用户可能会不小心勾选其他 app，必须按包名判断 “当前进程是不是哔哩哔哩” 才激活，否则会在错误进程里反射找不存在的类而报错。两个包名 hook 逻辑一样，共用一个 hooker。

Hook.kt：hook 逻辑

直接用框架的注入会非常方便：

  • class Hook : YukiBaseHooker()：一个 hooker 单元，onHook 里定义要 hook 什么。
  • "类全名".hook { }：按类名定位要 hook 的类（内部用反射找）。
  • injectMember { }：往类的某个成员（构造函数/方法）注入 hook，里面先声明要注入的成员，之后选择何时注入，以及具体注入的代码。
  • 选成员三种写法：allMembers(MembersType.CONSTRUCTOR) 选所有构造函数；method { name = "setUri"; param(StringClass) } 按名字 + 参数选方法；constructor { param(StringClass) } 按参数选构造函数。
  • beforeHook { } / afterHook { }：在方法执行前 / 后插入你的代码。

这里，首先注入了所有构造函数，afterHook：如果是 story 模式（竖屏的 uri），就改成 video 横屏。同时也注入了 setUri 方法的 beforeHook，每次更新竖屏 uri，都会直接改成横屏。

资源文件

模块能跑起来，除了 Main.kt / Hook.kt，还靠这几个文件：

  • assets/xposed_init：Xposed 标准。内容就一行，入口类全名（...hook.Entry）。LSPosed 加载模块时读它，决定实例化哪个类。没它 LSPosed 不知道从哪进。
  • assets/yukihookapi_init：YukiHookAPI 自己的。内容是 ...hook.Main，告诉 YukiHookAPI 哪个类是 IYukiHookXposedInit（即你的 Main）。
  • AndroidManifest.xml 里的 meta-data：声明这是个 Xposed 模块。
    • xposedmodule=true：标记本 APK 是 Xposed 模块（LSPosed 扫这个）。
    • xposeddescription：模块描述，LSPosed 列表里显示。
    • xposedscope：默认作用域（tv.danmaku.bili、com.bilibili.app.in），装模块时自动勾上这两个 App。
    • xposedminversion：要求的最低 Xposed API 版本。
  • res/values/strings.xml：app_name、app_desc，以及 scope 字符串数组（作用域包名），manifest 的 xposedscope 引用的就是它。作用域要和 Main.kt 里 loadApp 的包名、仓库根的 SCOPE 文件保持一致。
  • proguard-rules.pro：R8 混淆规则。Entry 和 Main 是靠字符串名字反射加载的，照理混淆器会把它们改名 / 删掉导致模块失效。但本模块这个文件基本是空的，因为 YukiHookAPI 库自带 consumer ProGuard 规则（随 AAR 自动应用）。

反编译定位

前文讲到，失效的原因是播放器路由时候 根本不看 uri 字段，直接拿了原始 avid 拼成 story/<id>。这个结论是反编译得到的。

  1. unzip bili.apk classes*.dex 先拆出所有 dex（8.60.0 有 34 个）。
  2. 直接用 grep -la 在所有 dex 的字符串池里搜 bilibili://story/，锁定有故事路由的 dex 文件。
  3. 再用 jadx 只解压这几个 dex。
  4. 定位到 RouteRequest$Builder — 所有 bilibili://story/ 的构造都经它手的构造函数。

观察到播放器路由有两类入口：

  • Feed 点击 → yd4.b.java:95（8.60.0，类名每版不同，反编译后会重排）："bilibili://story/" + displayParams.getAvid()。
  • 快捷方式 / 详情页切全屏 → 同样走 RouteRequest.Builder(String)。

只有一个出口，所以 hook 就放在那里。

  • 包名重命名：从 cn.wankkoree.xp.portrait2landscape 改为 com.zombie12138.nobiliportrait。涉及 applicationId、namespace、代码目录、package 声明、xposed_init/yukihookapi_init 里的 Entry/Main 类全名。构建验证通过后，APK 包名、KSP 生成的 Entry 都指向新路径。
  • 显示名：app_name 改 禁止竖屏 / No Bilibili Portrait。
  • Keystore：原版用的签名自然拿不到，重新生成自签名 keystore。
  • README rebrand：写明 fork 来源、适配 8.x 的原理、安装步骤。

构建和 CI

这里版本号改成了 3.0.0-dev，同时配置了 CI 自动发布 release 包。

workflow 触发：push v* tag。checkout 全历史（fetch-depth: 0，versionCode 需要），JDK 17 + Android SDK（platform-33 / build-tools 33.0.2），从 Secret 解码 keystore，gradlew assembleRelease 构建好后上传 APK 到 GitHub Release。

默认 GITHUB_TOKEN 只有读权限，创建 Release 返 403，需要 Action 配置中开启 “Read and write permissions”，workflow 显式加 permissions: contents: write。这样只要加一个 3.0.0 的 tag，然后 push 到 github 就自动构建发布了。

LSPosed 模块仓库提交

代码在 no-bili-portrait 维护，但 LSPosed manager 里能被搜索到的模块，是通过 Xposed-Modules-Repo 这个 GitHub 组织分发的——本质是另一个仓库，只用于 APK 分发，不放源码。本模块对应的是 Xposed-Modules-Repo/com.zombie12138.nobiliportrait。

  1. 去 官网 提交申请（prefilled issue），写明 fork 理由、包名、源码仓库，这样会自动生成一个 issue
  2. Bot 秒回，之后需要人工添加审核通过的标签，之后 bot 才会继续创建仓库添加权限。我几分钟就审批通过了，审核者是 yujincheng08，审核非常快。
  3. 在 Xposed-Modules-Repo/com.zombie12138.nobiliportrait 下放三个文件：SOURCE_URL（源码链接）、SUMMARY（一句话介绍）、README.md（模块说明），参考 官方 example 仓库。
  4. 推一个 git tag v3.0.0，在 Release 页创建 release、上传 APK。仓库 description 就是 LSPosed manager 里显示的模块名。
  5. 10 分钟内模块出现在 LSPosed manager 的模块库，可搜索、可直接下载安装。

Root 生态凋零和转机

Root 生态最近几年逐渐凋零：手机厂商逐渐关闭 BL 解锁的通道；开发者逐渐出走取消维护，比如我这次这个插件的原始作者，其实非常活跃，只是停止了更新；用户也大量出走。我一度对于 root 非常悲观，但让我对未来不那么悲观的一件事是：AI 对于 root 生态的转机。AI 能诞生更多插件，同时也能找到一些可利用的漏洞。

2026 年 7 月 7 日，Nebula Security 披露了 CVE-2026-43499 “GhostLock”：一个从 Linux 2.6.39（2011 年）存活至今的 futex 内核漏洞，影响所有 Linux 发行版，包括 Android。Google 给了 $92,337 的 kernelCTF 奖金。97% 的稳定率，约 5 秒拿到 root shell。更重要的是，Nebula 已经演示了 Android 上的完整链条：Firefox Android 浏览器漏洞（远程代码执行）→ GhostLock（本地提权到 root）= 点一个恶意链接 → 手机被 root。不需要解锁 BL、不需要 USB、不需要物理接触。但是这种如果想要实现 ksu 这种的持久的可以装插件系统开机自启动的 root，或者安装 ksu 这样的 root，不解锁 BL 情况下暂时是无法达到的。

心得

从十年前的一键 root，到最近几年的 Magisk、KernelSU、APatch 这些更现代的 root 工具，我之前从来没真正了解过原理，只知道 su 去请求 root 软件，通过就有 root，这次彻底理清楚了整个链路，现在我大概也能逐渐看懂一些具体的 root 配置的开关了。

我是和 AI 相互纠正完成的这个学习，过程和我之前的 交易原理 类似。由于用的是 ds-v4pro 这种模型，因此过程中非常多的事实错误。我只能检查逻辑是否自洽，是否和之前的知识冲突。之前的交易相关的主要是数学，只要推导没问题，结论没问题，就大概率没有问题。但是这个存在大量的工程实现细节，我对于 SELinux 不是非常熟悉，review 起来非常费力，而市面上文章很多存在过时的问题，直接看代码又太消耗精力或 token，最后我让 AI 通过实践来印证最终的猜想，整体也算勉强完成。本来有一章讲 root 隐藏的，但是由于太多待验证的内容，验证起来非常费时费力，不得不先删除。

同时学习过程中我也注意到，我了解 root 如何运作，了解修复过程，但是中间反编译去定位问题的细节我从来没有深度参与。由于代码方便验证和检索，AI 对于这种代码的问题往往不容易出现太多幻觉，我也就不看。这部分也是需要很多经验和耐心，有了 AI 之后，这部分的技能很难被继续训练了。但是这些细节的技能，未来真的是否需要人亲自参与也很难说。
